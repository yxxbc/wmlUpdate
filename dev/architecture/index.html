    Architecture¶

    Goals¶

    1. A small Go library that embeds in an existing application without taking over its architecture.
    2. One codebase covering Windows, macOS and Linux.
    3. A stable contract for non-Go languages through optional adapters.
    4. Authenticated metadata and verified artifacts.
    5. Safe, recoverable installation.
    6. Useful diagnostics, not silent failure.

    Non-goals¶

    • A framework or application runtime. The SDK exposes Check and Apply; the host owns UI, lifecycle and restart.
    • A required daemon or service. The CLI/HTTP adapters are optional.
    • Delta updates. A full artifact is downloaded; content-addressed caching avoids re-downloading the same bytes.
    • A system-wide scheduler. The host application decides when to check.
    • Arbitrary package-manager integration. The command strategy can invoke one, but rollback is owned by that installer.
    • Code signing. The updater preserves bytes; macOS notarization and Windows Authenticode signing remain part of your release pipeline.
    • A hosted update service. Any static web server is sufficient.

    Component map¶

    github.com/yxxbc/wmlUpdate (package wmlupdate)
  └─ public SDK: New, Check, Apply, Options, Config, Event
       └─ internal/engine ──────── orchestration, checked snapshots, results
            ├─ internal/source ──┬─ github.go   Releases API + checksums
            │                    ├─ static.go   signed manifest + mirrors
            │                    └─ chain.go    ordered failover
            ├─ internal/httpx ──── hardened client, retry, resumable download
            ├─ internal/manifest  manifest model, validation, signature
            ├─ internal/checksum  SHA-256 and sha256sum parsing
            ├─ internal/install ─┬─ Prepare    staging / extract / preserve
            │                    └─ Apply      journal, backup, swap, rollback
            ├─ internal/archive   safe zip/tar extraction and creation
            ├─ internal/state     atomic JSON state and install journal
            ├─ internal/lock      per-app advisory lock
            └─ internal/sign      Ed25519 keys and detached signatures

cmd/wml-update
  └─ internal/cli ──────────────── commands, release tooling, sidecar adapter
       ├─ internal/engine ──────── same engine as the SDK
       └─ internal/api ─────────── optional loopback HTTP API, jobs, SSE

internal/publish ───────────────── release archive/manifest/checksum tooling

    The SDK is the primary product. cmd/wml-update is optional: it packages releases (publish, keygen, sign, verify) and exposes the same engine to non-Go languages through NDJSON and HTTP. It does not participate in a Go application's runtime unless the application chooses the sidecar mode.

    Supporting packages: internal/version (strict SemVer), internal/platform (normalization and asset heuristics), internal/event (event contract), internal/config (strict JSON loading, programmatic preparation, validation), internal/buildinfo (ldflags).

    Public SDK surface¶

    type Options struct {
    ConfigPath, BaseDir, CurrentVersion string
    Config   *Config
    Platform *Platform
    Events   EventFunc
}

func New(Options) (*Updater, error)
func (*Updater) Check(context.Context) (*Update, error)
func (*Updater) Apply(context.Context, *Update, ApplyOptions) (*Result, error)
func (*Updater) Close()

    Update is an opaque checked snapshot: public fields are informational, while the exact release and selected asset are retained privately. Apply validates and uses that snapshot, so a source change between Check and Apply cannot swap the artifact silently. Update values are not serializable.

    Update flow¶

    Check / Apply
   │
   ├─ load strict config, resolve target platform
   ├─ determine current version (explicit > state > config)
   ├─ Check: fetch metadata, select asset, compare versions (read-only)
   ├─ Apply: acquire per-app lock
   ├─ recover interrupted transaction (if any)
   ├─ use the exact checked release snapshot (no metadata re-fetch)
   ├─ download to state/downloads with Range resume and retry
   ├─ verify size + SHA-256 (and authenticated hash source)
   ├─ install strategy:
   │    ├─ directory: extract → preserve → journal → swap → backup
   │    ├─ file:      stage → journal → backup → rename
   │    ├─ command:   run verified installer
   │    └─ external:  return artifact path
   └─ record state, optional relaunch, emit result

    Trust model¶

    The source URL and configuration are trusted; everything fetched over the network is untrusted.

    1. Metadata authenticity
    2. Self-hosted manifests are signed with Ed25519 when a public key is configured. The signature covers the exact raw bytes, so whitespace and key ordering are not ambiguous.
    3. GitHub metadata is authenticated by TLS and the GitHub API. Hash strength is improved by requiring the API's asset digest or a checksums.txt asset. An optional signed checksums file provides an independent trust anchor.
    4. Artifact integrity
    5. Every download requires a SHA-256. Downloading is refused otherwise unless the dangerous allow_unverified_assets flag is set.
    6. The hash is taken from a signed manifest, a signed checksums file, or GitHub's API digest.
    7. Network boundaries
    8. HTTPS is required except loopback or explicit opt-in.
    9. Redirects are re-evaluated against scheme, host allowlist and count.
    10. Authorization headers are not forwarded to a different host by Go's redirect policy; self-hosted headers are only attached to same-host assets at the model layer.
    11. Filesystem safety
    12. Archive extraction rejects absolute paths, Windows volume paths, .. traversal, escaping symlinks, hardlinks, device/FIFO entries, duplicate symlink-parent writes, excessive entries and excessive expansion.
    13. Install targets are validated against filesystem root, the home directory, symlink targets and state-directory overlap.
    14. Staging and backups are siblings of the target, keeping renames on one filesystem.
    15. Local API
    16. Bearer token required, constant-time comparison.
    17. Loopback bind by default; remote binding requires an explicit flag.
    18. No CORS policy is added, so browser origins cannot call it cross-site without the token.

    Installation transaction¶

    State is kept in <state_dir>/state.json. Before any live rename, a pending journal records target, stage, backup, versions and phase.

    Directory / file replace¶

    1. prepared: artifact verified, new tree staged; live target untouched.
    2. Rename target → backup (backed_up saved).
    3. Rename stage → target (committed saved).
    4. Append backup metadata, write installed version, clear journal.
    5. Prune backups beyond keep_backups.

    On failure, the backup is restored. On the next mutating command, recovery inspects the journal:

    • prepared with backup present and target missing: restore backup.
    • backed_up with target present and stage gone: the swap completed; finalize.
    • Otherwise: restore the backup and remove partial staged data.
    • Command installers are not recoverable; the journal is cleared with a warning telling the operator to verify the application manually.

    Backups are retained as siblings of the target so rollback requires only renames. rollback moves the current installation aside and restores the latest backup.

    Why a detached helper¶

    On Windows, a running executable and loaded DLLs cannot be replaced, and the updater itself may live inside the application directory. With --defer:

    1. The parent updater downloads, verifies, extracts and writes a plan.
    2. It copies its own executable into the state directory.
    3. It starts the copied helper detached with --wait-pid values, then exits.
    4. The helper waits for the application to exit, acquires the lock, runs the same journaled apply path, optionally relaunches, and writes a result file.

    This avoids depending on a helper inside the tree being replaced.

    State and concurrency¶

    • One advisory lock per app_id serializes mutating operations across processes.
    • API jobs reject a second mutating job; the CLI additionally uses the file lock.
    • state.json writes are atomic (temp file, fsync, rename, directory fsync).
    • Source metadata uses ETag/Last-Modified caches stored under the state directory.
    • Downloads are named by expected SHA-256, so concurrent or repeated checks do not trust stale content.

    Result and event contract¶

    --json writes one JSON object per line:

    • log, warning, progress: progress is download with bytes, total, percent.
    • result: exactly one terminal successful object.
    • error: terminal failure with a stable code.

    The same shapes are returned by the HTTP job API. See integration.

    Exit codes¶

    Code Meaning
    0 Success
    1 Internal error / diagnostics failure
    2 Usage or configuration error
    3 Source, network, no release or no matching asset
    4 Integrity / signature / checksum failure
    5 Installation or rollback failure
    6 Lock, state or I/O failure
    130 Cancelled

    Extension points¶

    • New source: implement source.Provider and normalize to release.Release.
    • New installer: add a strategy to config validation, Prepare and Apply, with a journal phase and rollback semantics.
    • New API: the engine is independent of Cobra and HTTP.
